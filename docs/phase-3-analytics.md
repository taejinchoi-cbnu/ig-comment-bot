# Phase 3 — 성과 분석 ★

> **상태**: 대기   |   **선행**: Phase 2
>
> **완료 기준**: 지인이 "이 게시글 효과 있었어?"에 **대시보드만 보고** 답한다.

## 목표

**이게 이 프로젝트의 존재 이유다.**

지인들이 상용 서비스에 불만이었던 건 자동 DM 기능이 아니라 **"효과가 있었는지 알 수가 없다"** 였다
([`why.md`](./why.md)). Phase 1~2는 여기 쓸 데이터를 모으기 위한 준비였다.

우리가 유리한 이유는 하나다 — **원천 이벤트를 전부 `Event` 테이블에 갖고 있다.**
상용 서비스는 대시보드가 범용이라 이 퍼널을 그대로 보여주지 않고 내보내기도 제한적이다.

## 할 일

### 1. 퍼널 집계
- [ ] 게시글별 `댓글 → DM 발송 → 답장 → 양식 발송` + 각 단계 전환율
- [ ] SQL `GROUP BY` 하나로 끝난다. 미리 집계 테이블을 만들지 않는다

```sql
SELECT media_id, type, count(*) AS n, count(DISTINCT igsid) AS people
  FROM events
 WHERE ig_account_id = $1 AND created_at >= $2
 GROUP BY media_id, type;
```

- [ ] 대시보드의 각 게시글 줄에 그대로 표시 → **별도 분석 페이지를 만들지 않는다** (원칙 1)
- [ ] 기간 필터 (오늘 / 7일 / 30일 / 전체)
- [ ] 게시글 정렬 — "어떤 게시글이 제일 잘 됐어?"

### 2. "왜 DM이 안 갔지?"에 답하기
- [ ] `COMMENT_SKIPPED` 집계를 게시글별로 노출
- [ ] `skipReason`을 사람 말로 매핑

| `skipReason` | 화면 표시 |
|---|---|
| `SELF_COMMENT` | 본인이 단 댓글이라 보내지 않았어요 |
| `NO_KEYWORD_MATCH` | 설정한 키워드가 댓글에 없었어요 |
| `DUPLICATE` | 이미 보낸 댓글이에요 |
| `CAMPAIGN_DISABLED` | 이 자동 DM이 꺼져 있었어요 |

- [ ] 실패(`FAILED`)도 같은 방식으로 — `errorCode` → "인스타 권한이 없어요" / "댓글이 7일 지났어요"

### 3. CSV 내보내기
- [ ] 기간 + 게시글 필터 → `events` CSV 다운로드
- [ ] 컬럼: 시각 · 게시글 · username · 무슨 일 · 사유
- [ ] **본문은 넣지 않는다** ([`architecture.md`](./architecture.md) 개인정보 원칙)
- [ ] 지인들이 결국 엑셀로 본다. 체감 가치 대비 구현량이 가장 큰 항목

### 4. ★ 지인에게 물어보기
- [ ] 화면을 보여주고 **"이거 보고 뭐가 더 궁금해요?"** 를 묻는다
- [ ] 답을 `진행 기록`에 그대로 적고, 그중 SQL로 답할 수 있는 것부터 만든다
- [ ] 사용자가 5명이라 가능한 일이고, **상용 서비스가 구조적으로 못 하는 부분**이다

## 하지 않을 것

- **차트 라이브러리** — 원칙 2대로 표와 문장으로 먼저 답한다. 지인이 "그래프로 보고 싶다"고 말할 때 넣는다
- **집계 테이블 / 캐시** — 이벤트가 수천 건 규모다. `GROUP BY`가 느려지면 그때
- **별도 분석 페이지** — 대시보드 한 화면에서 답한다

## 검증

- [ ] 지인에게 대시보드만 주고 **"지난주 어느 게시글이 제일 잘 됐어요?"** 를 물어본다. 설명 없이 답하면 성공
- [ ] "왜 DM이 안 갔어요?" 질문에 대시보드가 답하는지
- [ ] CSV를 엑셀에서 열어 한글이 깨지지 않는지 (UTF-8 BOM)
- [ ] 퍼널 숫자가 실제 DM 발송 이력과 일치하는지 수동 대조
