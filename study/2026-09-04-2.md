# 파이프라인이 돌기 시작하자 설계 가정 세 개가 틀린 게 드러났다

> 2026-09-04 ~ 09-05 · Phase 1, 실계정 운영 이후
>
> [1편](./2026-09-04-1.md)은 "로컬에서 맞는 것이 실제 환경에서 맞지 않았다"였습니다.
> 이번은 다른 종류입니다 — 실제 환경에서 잘 돌았는데, **돌고 나서야 설계가 틀렸다는 게
> 보였습니다.**

## 배경

댓글 → 자동 DM → 답장 → 양식 발송이 실계정에서 관통했고, 앱에 역할이 없는 제3 계정에서도
동작하는 것까지 확인했습니다. 그때부터 나온 게 이 문서의 내용입니다.

바뀐 것 세 가지입니다.

| | 무엇이 틀렸나 | 언제 알았나 |
|---|---|---|
| 1 | 중복 방지 키가 `commentId` — 같은 사람이 같은 글에 또 달면 DM 이 또 나감 | 사용자가 "중복 발송 막는 로직 체크해줘" 라고 물었을 때 |
| 2 | DM 이 상대의 "요청" 탭으로 가서 **받은 줄 모름** | 첫 관통 직후, "DM 이 안 오는데" 라는 말에서 |
| 3 | 팔로워 여부를 기억하지 않아 같은 사람에게 확인 메시지를 반복 | 사용자가 KV 저장소 도입을 제안하면서 |

그리고 코드 리뷰와 실사용이 **제가 그 과정에서 새로 만든 회귀 세 개**를 잡았습니다.
그쪽이 이 문서에서 더 값어치 있는 부분입니다.

## P — Problem

### 1. Meta 는 "댓글당 1회" 를 보장하는데, 그게 우리가 원한 보장이 아니었다

사용자의 질문은 이거였습니다.

> "이미 디엠 보내면 댓글 또 달아도 발송 안되게"

코드를 확인해보니 멱등성 마커의 키가 `(igAccountId, commentId)` 였습니다.

```
xowls0002026 → 댓글 "예약"  (commentId A) → DM 발송 ✅
xowls0002026 → 댓글 "저요"  (commentId B) → DM 또 발송 ⚠️
```

**Meta 도 막아주지 않습니다.** Private Reply 제한은 "댓글당 1회"([`meta-api.md`](../docs/meta-api.md)
§1-9)라서 새 댓글에는 새 허용이 붙습니다. 즉 이 키가 유일한 방어선인데, 방어하는 대상이
"중복 웹훅" 이지 "같은 사람의 반복 댓글" 이 아니었습니다.

원래 문서에는 이렇게 적혀 있었습니다 — *"멱등성 — 중복 댓글 1회만 발송"*.
"중복 댓글" 이 무엇을 뜻하는지 정하지 않은 채 구현했고, 코드는 좁은 쪽으로 해석했습니다.

### 2. 발송에 성공했는데 사용자는 못 받았다고 했다

첫 관통 직후였습니다. DB 에는 `PRIVATE_REPLY_SENT`, `errorCode` 없음, Instagram API 가 200.
그런데 "디엠이 안 와" 였습니다.

답은 이미 우리 문서에 있었습니다. [`meta-api.md`](../docs/meta-api.md) §6 트러블슈팅
결정 트리의 **마지막 줄**입니다.

```
└─ 성공 → 상대방 요청함(Requests) 탭 확인
```

Private Reply 는 받은편지함이 아니라 **"요청" 탭**으로 갑니다. 발송은 성공했고 사람은
못 봤습니다. 이건 버그가 아니라 **제품 문제**였습니다.

### 3. 같은 사람에게 매번 "팔로워인지 확인할게요" 를 보냈다

1차 DM 이 "팔로워인지 확인할게요! 아무 메시지나 보내주세요 💬" 인 이유는 플랫폼 제약입니다.
`is_user_follow_business` 는 **대화가 성립한 뒤에만** 조회됩니다(§1-13). 댓글 시점에는
그 사람이 팔로워인지 알 방법이 없어서, 일단 말을 걸어 대화를 만드는 게 1차 DM 의 역할입니다.

문제는 **그 다음에도 계속 모른다는 것**이었습니다. 같은 사람이 다음 게시물에 댓글을 달면
또 처음부터입니다. 우리가 기억을 못 하는 건데 사용자에게는 우리가 멍청해 보입니다.

## A — Analysis

### 키를 무엇으로 잡아야 하는가

세 후보를 놓고 각각이 무엇을 깨뜨리는지 봤습니다.

| 키 | 같은 글에 두 번째 댓글 | 다른 글에 댓글 |
|---|---|---|
| `commentId` (기존) | DM 또 나감 ❌ | 나감 ✅ |
| `igsid` | 안 나감 ✅ | **영영 안 나감** ❌ |
| **`igsid + mediaId`** | **안 나감** ✅ | **나감** ✅ |

`igsid` 만으로 잡으면 "한 번 DM 받은 사람은 다른 게시물의 문구를 영영 못 받는다" 가 됩니다.
게시물별 문구는 이 제품의 핵심 기능인데 그게 죽습니다.

`(계정, 사람, 게시물)` 이 제품의 멘탈 모델과 정확히 겹칩니다 —
**"한 게시글 = 한 자동 DM"**([`why.md`](../docs/why.md)).

### 저장소를 새로 둘 것인가

팔로워 캐시에 대해 사용자가 제안한 건 이거였습니다.

> "TTL을 두고 key:value DB에 간단하게 저장하는건 어때?"

방향은 맞는데 **저장소가 이미 있었습니다.** `Conversation` 이
`@@unique([igAccountId, igsid])` 라 **사람당 한 행**입니다. 그 행이 곧 key-value 이고,
컬럼 두 개면 값과 만료 시점이 다 들어갑니다.

```prisma
isFollower        Boolean?
followerCheckedAt DateTime?
```

TTL 도 만료 배치가 아니라 읽는 시점의 비교 한 줄입니다.

```ts
now - checkedAt.getTime() < ttlMs
```

Redis 나 DynamoDB 를 붙이면 인프라·비용·장애 지점이 늘어나는데, 저장할 데이터는 계정당
수백 행입니다. **새 의존성이 값을 못 합니다.**

여기서 하나 더 발견했습니다 — **`is_user_follow_business` 를 그때까지 아무 데서도 조회하지
않고 있었습니다.** Phase 3 항목이 문서에만 있었습니다. 캐시를 넣으려면 값부터 있어야 해서
조회를 붙였고, 그러면서 Phase 3 의 그 항목과 `Event.isFollower` 박제가 함께 닫혔습니다.

### 안 만들기로 한 것: 댓글 좋아요

사용자 요청은 *"코멘트에 하트 누르고 DM 발송 완료! 로"* 였습니다.
공식 문서를 확인했더니 댓글 노드에 가능한 쓰기는 셋뿐이었습니다.

| 작업 | 엔드포인트 |
|---|---|
| 대댓글 | `POST /{comment-id}/replies` |
| 숨기기/해제 | `POST /{comment-id}` |
| 삭제 | `DELETE /{comment-id}` |

**좋아요 엔드포인트는 존재하지 않습니다.** 만들 수 없다는 걸 확인하고 그대로 보고했습니다.
추측으로 시도했으면 400 을 받고 원인을 찾느라 시간을 썼을 겁니다.

### 기본값을 무엇으로 둘 것인가 — 팔로워 게이트

"비팔로워도 옵션으로 막을 수 있게" 라는 요청이었습니다. **켤 수 있게 만드는 것과 기본으로
켜는 것은 다른 결정**이라 나눴습니다.

기본을 끔으로 둔 근거 세 가지입니다.

| | |
|---|---|
| 개념이 는다 | 켜는 순간 사용자는 "팔로워 게이트" 를 배워야 합니다. 기본값이면 **모두가**, 옵션이면 원하는 사람만 배웁니다 ([`why.md`](../docs/why.md) 원칙 1) |
| **잘못 막는 비용이 비대칭** | 게이트가 없으면 비팔로워가 양식을 받습니다(손해 작음). 게이트가 잘못 막으면 **진짜 고객을 놓칩니다**(손해 큼) |
| 판단이 항상 가능하지 않다 | 조회 실패 시 값은 `null` 입니다. **이때도 막지 않습니다** — API 한 번 실패로 정상 사용자를 막는 쪽이 훨씬 나쁩니다 |

## A — Action

### 키 교체와 마이그레이션

```prisma
@@id([igAccountId, commentId])  →  @@id([igAccountId, igsid, mediaId])
```

`commentId` 는 컬럼으로 남기되 키에서 뺐습니다 — 어느 댓글이 발동시켰는지는 계속 알아야
하니까요.

마이그레이션은 손으로 썼습니다. `igsid`/`mediaId` 를 NOT NULL 로 추가하려면 기존 행에 채울
값이 있어야 하는데 없어서, 맨 앞에 `DELETE FROM "SentReply";` 를 넣고 **왜 지우는지를
마이그레이션 파일에 적었습니다.**

> 마커는 본래 휘발성이라 지워져도 "그 사람이 그 글에 한 번 더 받을 수 있다" 가 전부입니다.

### 공개 대댓글 — 부가 동작이 주 동작을 되돌리면 안 된다

"요청 탭" 문제의 답은 **댓글에 공개로 한 줄 다는 것**이었습니다. "DM 확인해보세요" 신호가
공개적으로 남습니다.

설계에서 신경 쓴 건 두 가지입니다.

**절대 던지지 않습니다.** 거기 도달했다는 건 DM 이 이미 나갔다는 뜻입니다. 던지면 SQS 가
재시도하고, 재시도는 멱등성 마커에 막혀 `DUPLICATE` 스킵만 쌓입니다.

**`Event` 도 남기지 않습니다.** `FAILED` 로 쓰면 "DM 발송 실패" 와 섞여 Phase 3 퍼널이
오염됩니다. 전용 타입을 만들 필요는 아직 확인되지 않았으니 로그로만 남겼습니다.

무한루프는 없습니다 — 우리가 단 대댓글은 셀프 댓글이라 `normalize.ts` 가 이미 거릅니다.

### opt-in 을 기본형으로

대댓글도 게이트도 **`null` 이면 동작하지 않습니다.**

```prisma
defaultCommentReplyText String?   // null 이면 대댓글 안 담
nonFollowerText         String?   // null 이면 아무도 안 막음
```

설정하지 않은 사용자의 동작이 그대로라는 뜻이고, 새로 배울 개념이 생기지 않는다는 뜻입니다.

## 내가 만든 회귀 세 개

여기가 이 회차에서 가장 값어치 있는 부분입니다. **키를 넓히는 변경이 그 키에 딸린 다른
로직들을 조용히 깨뜨렸는데, 저는 그걸 못 봤습니다.**

### 1. non-retryable 실패가 (사람, 게시물)을 영구 소각 — 코드 리뷰가 발견

기존 코드는 발송이 non-retryable 로 실패하면 **마커를 남겨뒀습니다.** "재시도해도 성공하지
않으므로" 라는 이유였고, `commentId` 키에서는 손해가 그 댓글 하나였습니다.

키를 넓히자 같은 코드의 의미가 달라졌습니다.

> 토큰이 잠깐 403 (→ `errors.ts` 가 비재시도로 분류) → 마커 남음 →
> **토큰을 고쳐도 그 사람은 그 게시물에서 영영 DM 을 못 받음**

원인은 마커에 **두 가지 뜻을 겹쳐 담은 것**이었습니다 — "이미 보냄" 과 "이 시도는 가망
없음". 앞의 뜻만 남기고 발송 실패 시에는 양쪽 분기 모두 마커를 지우도록 고쳤습니다.

### 2. 최적화가 자기 자신을 무력화 — 코드 리뷰가 발견

빠른 경로는 대화를 `FORM_SENT` 로 시작합니다. 그런데 `handleMessage` 의 조건부 UPDATE 는
`WAITING_USER_MESSAGE` 에서만 선점하므로, 그 사람이 양식에 답장하면 **`count === 0` 으로
빠져나가 `checkFollower` 에 영영 도달하지 못합니다.**

즉 **최적화 대상인 단골에게서만 캐시가 만료되고 다시는 갱신되지 않습니다.**

고치면서 개념 하나를 나눠야 했습니다. "팔로워임" 과 "이 값이 신선함" 은 다른 질문입니다.
비팔로워로 확인된 사람도 확인 자체는 신선한데, 뭉쳐서 판단하면 그 사람 답장마다 조회가
나갑니다.

### 3. 캐시가 자기 메시지의 결과를 못 따라감 — 실사용이 발견

사용자가 팔로우한 뒤 새 게시물에 댓글을 달았는데 **같은 확인 문구가 또 나갔습니다.**

캐시에 `false` 가 4분 전에 기록돼 있었고 TTL 이 30일이었습니다. 댓글 경로는 캐시를 읽기만
하므로 다시 물어볼 계기가 없었습니다.

**두 값이 같은 속도로 늙지 않는다**는 걸 놓쳤습니다.

| 값 | 성질 | TTL |
|---|---|---|
| `true` | 팔로우는 잘 안 끊김 | 30일 |
| `false` | **우리 1차 DM 이 바꾸라고 시키는 값** | 1시간 |

"팔로우해달라" 고 해놓고 시키는 대로 한 사람에게 30일 동안 같은 걸 또 묻는 건 앞뒤가
맞지 않습니다. 만료됐고 대화가 있으면 댓글 시점에 다시 조회하도록 했습니다.

## 리뷰 결과를 그대로 믿지 않은 것

`/code-review medium` 이 7건을 냈고 **1건은 반증했습니다.**

> `connect-account.ts` 가 `ops/deploy.env` 를 소스하지 않아 자리표시자 URL 을 출력한다

`prisma/client.ts` 가 `import './../env.ts'` 를 하고, 그 모듈 부작용이 `main()` 보다 먼저
dotenv 를 돌립니다. 실측으로 `AWS_PROFILE` 이 채워지고, 실제 실행에서 **진짜 Function URL 이
출력됐습니다.** 무효 처리했습니다.

순위도 다시 매겼습니다. 리뷰가 HIGH 로 놓은 "게이트 재발송 루프" 는 **게이트가 기본으로
꺼져 있어 오늘 아무에게도 영향이 없습니다.** 반대로 MEDIUM/LOW 로 매겨진 것 중 둘이
기본 경로에서 지금 터지고 있었습니다(위의 회귀 1·2번). **심각도는 코드가 아니라 배포된
설정에서 나옵니다.**

리뷰가 잡은 것 중 하나는 코드가 아니라 문서였습니다 — 제가 쓴 개인정보처리방침에
"이메일을 수집하지 않습니다" 라고 적혀 있는데 `User.email` 이 실재합니다. **공개된 법적
문서가 PII 에 대해 틀린 말을 하고 있었고**, 한 줄 고쳤습니다.

## 배운 것

### 1. 키를 바꾸면 그 키에 딸린 실패 처리도 같이 봐야 한다

`SentReply` 의 키를 넓힌 변경은 스키마·핸들러 두 줄·테스트가 전부로 보였습니다.
실제로는 **같은 파일 30줄 아래의 에러 처리 의미가 바뀌었습니다.**

"이 값의 범위가 넓어지면, 이 값을 쓰는 다른 코드가 감당하는 범위도 넓어진다" —
검색해서 호출부를 다 봤는데도 못 잡았습니다. 호출부가 아니라 **의미의 사용처**였기
때문입니다.

### 2. 최적화는 자기 전제를 깨뜨릴 수 있다

캐시를 쓰는 빠른 경로가 캐시를 채우는 경로를 막았습니다. 개별 단계는 다 맞는데
사이클로 보면 자기모순입니다. **"이 최적화가 걸린 뒤에도 이 최적화를 유지하는 입력이
계속 들어오는가"** 를 물었어야 했습니다.

### 3. 캐시의 TTL 은 값마다 다를 수 있다

하나의 TTL 을 두는 게 당연해 보였는데, `true` 와 `false` 는 바뀌는 속도가 다릅니다.
특히 **`false` 는 우리 제품이 직접 바꾸라고 요구하는 값**이었습니다. 시스템이 스스로
바꾸라고 요청한 값을 오래 캐시하면 자기 요청을 무시하게 됩니다.

### 4. 기본값 선택은 코드가 아니라 제품 결정이다

팔로워 게이트를 만드는 것과 켜는 것을 나누고 나서야, 기본을 끄는 근거를 문장으로 쓸 수
있었습니다 — 개념이 는다, 잘못 막는 비용이 비대칭이다, 판단이 항상 가능하지 않다.
그래서 [`why.md`](../docs/why.md) 에 **제품 결정 섹션으로** 남겼습니다. 코드 주석에만
있었으면 다음에 "기본으로 켜자" 는 말이 나왔을 때 반박할 근거가 없습니다.

### 5. 리뷰 결과는 검증 대상이지 결론이 아니다

7건 중 1건이 틀렸고, 심각도 순위는 절반이 어긋나 있었습니다. 리뷰는 코드를 보지만
**무엇이 배포돼 있고 어떤 설정이 켜져 있는지는 모릅니다.** 반증에 쓴 시간은 5분이었고,
그걸 안 했으면 멀쩡한 코드를 고칠 뻔했습니다.

## 면접용 30초 요약

> 자동 DM 파이프라인이 실계정에서 돌기 시작한 뒤, 중복 발송 방지 키가 잘못 잡혀 있다는 걸
> 발견했습니다. 키가 댓글 ID 라서 같은 사람이 같은 게시물에 댓글을 또 달면 DM 이 다시
> 나갔고, 플랫폼도 그건 막아주지 않았습니다. 키를 **(계정, 사람, 게시물)** 로 바꿔 제품의
> "한 게시글 = 한 자동 DM" 모델과 맞췄습니다.
>
> **문제는 그 변경이 만든 회귀였습니다.** 기존 코드는 발송이 영구 실패하면 마커를 남겼는데,
> 좁은 키에서는 손해가 댓글 하나였지만 넓힌 키에서는 **그 사람이 그 게시물에서 영영 DM 을
> 못 받는** 결과가 됩니다. 마커에 "이미 보냄" 과 "가망 없음" 두 뜻이 겹쳐 있던 게 원인이라
> 앞의 뜻만 남겼습니다. 코드 리뷰가 잡아준 건이고, 같이 나온 7건 중 1건은 근거를 실측해서
> 반증했습니다.
>
> 팔로워 여부 캐시에서는 **새 저장소를 도입하자는 제안을 기존 테이블로 대체**했습니다.
> 대화 테이블이 이미 사람당 한 행이라 컬럼 두 개면 key-value 가 되고, TTL 도 만료 배치
> 없이 읽는 시점 비교로 끝납니다. 이후 캐시가 자기 전제를 깨는 문제와, 우리 메시지가
> 바꾸라고 요청한 값을 30일 캐시하는 모순을 실사용에서 찾아 **값에 따라 TTL 을 다르게**
> 두는 것으로 고쳤습니다.
