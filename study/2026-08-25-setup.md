# 검증하지 않은 설계서로 구현에 들어갈 뻔한 하루 — 코드 대신 방향을 세 번 바꿨습니다

> ig-comment-bot (인스타그램 댓글 → 자동 DM + 성과 분석) · 2026-08-25
> Phase 0 (설계 검증 · 문서화 · 인프라 세팅)

**PAAR 구조**로 정리합니다 — Problem(문제) · Analysis(분석) · Action(조치) · Result(결과).

---

## 배경

지인들이 인스타그램 상용 자동 DM 서비스(매니챗, 소셜비즈 등)를 쓰면서 불편을 이야기했고,
그걸 직접 만들어보기로 했습니다. 시작 시점에 가진 것은 **설계 문서 하나(2,077줄)** 뿐이었고,
저장소에는 커밋이 0개였습니다.

설계서에는 아키텍처, Meta API 사용법, 상태 머신, DynamoDB 스키마, 배포 파이프라인까지
구현에 필요한 내용이 다 있어 보였습니다. 그래서 바로 Phase 1(구현)에 들어갈 계획이었습니다.

---

## P — Problem

**그 설계서가 검증된 적이 없었습니다.**

설계서는 잘 읽혔습니다. 표와 다이어그램이 있고 API 예제까지 붙어 있어서
"이대로 짜면 되겠다"는 인상을 줬습니다. 문제는 그 인상이 근거가 아니라는 것이었습니다.

그리고 더 근본적인 문제가 하나 더 있었습니다.
**만들려는 것이 무엇인지가 틀려 있었습니다.**

지인들이 한 말은 두 가지였습니다.

- 쓰기가 어렵다
- 통계가 어렵다

**"자동 DM 기능이 부족하다"는 말은 없었습니다.** 그런데 제 설계서는 처음부터 끝까지
자동 DM을 어떻게 보낼 것인가에 대한 문서였고, 분석은 마지막 Phase의 선택 항목이었습니다.

즉 문제가 두 층이었습니다.

1. **어떻게 만들 것인가**가 사실과 다르게 적혀 있었다
2. **무엇을 만들 것인가**가 사용자가 말한 것과 어긋나 있었다

## A — Analysis

### 1단계: 설계서를 공식 문서와 한 줄씩 대조했습니다

구현 전에 Meta 공식 문서로 설계서의 API 관련 서술을 검증했습니다.
**5개가 사실과 달랐고, 전부 "조용히 실패하는" 종류였습니다.**

| 설계서 내용 | 실제 | 그대로 짰다면 |
|---|---|---|
| 댓글 payload가 `entry[].field` | `entry[].changes[].field`, IGSID는 `value.from.id` | 파싱 자체가 실패 |
| echo 필터 언급 없음 | 봇이 보낸 DM이 `message.is_echo`로 되돌아옴 | **무한루프** |
| 계정 구독 단계 없음 | 계정마다 `POST /me/subscribed_apps` 필요 | webhook이 **아예 안 옴** |
| webhook 권한이 `sqs:SendMessage`뿐 | HMAC 검증에 App Secret이 필요 | 서명 검증 불가 |
| "팔로워 판별 API는 없다" | `is_user_follow_business` 존재 | 기능 하나를 놓칠 뻔 |

특히 위험한 건 3번이었습니다. Meta 대시보드에서 `comments`, `messages` 필드를 구독하면
설정이 끝난 것처럼 보이지만, **계정 단위 구독 API를 따로 호출하지 않으면 이벤트가 한 건도 오지 않습니다.**
에러도 나지 않고 그냥 조용합니다. 이걸 모르고 구현했다면 "webhook이 안 온다"는 증상만 들고
서명 검증, IAM 권한, API Gateway 설정을 며칠 뒤졌을 겁니다.

2번(echo 필터)은 더 나쁩니다. 봇이 보낸 DM이 다시 webhook으로 들어오는데,
필터가 없으면 자기 메시지에 자기가 반응하는 무한루프가 됩니다.
테스트 계정으로 돌렸다면 실제 사용자에게 DM이 무한 발송될 수 있는 종류의 버그였습니다.

### 2단계: 시장을 조사했더니 사업이 성립하지 않았습니다

원래는 "AWS 배포가 어려운 사람 대신 운영해주고 비용을 받는" 모델을 생각했습니다.
그래서 한국에 같은 서비스가 있는지 확인했습니다.

**댓글 → 자동 DM을 이미 서비스 중인 한국 업체가 9곳이었습니다.**

| 서비스 | 운영 | 가격 |
|---|---|---|
| 리틀리 | 링크인바이오 | **완전 무료** |
| 소셜비즈 | **NHN DATA** (대기업) | 팔로워 200명 기준 월 5,000원~ |
| 포크레터 | 소규모 | 무료 / ₩4,900 / ₩16,900 · **9,389+ 크리에이터** |
| Conma | 한국 SaaS | 월 ₩5,900 |
| 소시안 · 인포크 · 키티챗 · 센드비 · 와이어디 | 한국 | 월 2,900원 ~ 18,900원 |

여기에 매니챗도 한국에서 널리 쓰입니다.
**한국어 UI를 갖춘 대기업 서비스와 완전 무료 옵션이 동시에 존재하는 시장**이었습니다.
1인 개발자가 유료로 진입할 자리가 없었습니다.

### 3단계: 그런데 같은 조사가 진짜 빈자리를 알려줬습니다

상용화를 접기로 하고 조사를 계속했더니, 매니챗 사용자 리뷰에서 이 문장이 나왔습니다.

> 콘텐츠 스케줄링, 캘린더, 팀 승인, **분석 리포팅은 전부 매니챗 밖에서 일어난다.**
> 매니챗과 SocialPilot을 함께 쓰는 것이 흔한 에이전시 구성이다.

**시장 1위가 분석을 제품 밖으로 밀어낸 상태였습니다.** 사용자들이 별도 도구를 붙여 쓰고 있었습니다.

그 밖의 불만도 기능 부족이 아니라 다른 곳에 몰려 있었습니다.

- **연락처 수 기준 과금 — 메시지를 보내지 않아도 청구됩니다.** 스팸·봇 계정까지 카운트되어
  리스트가 커지면 청구액이 2~3배가 됩니다
- **2026년 3월 무료 플랜을 1,000명 → 25명으로 축소**했습니다
- **플로우가 실행되지 않으면 리드가 조용히 유실됩니다**

마지막 항목이 눈에 들어왔습니다. 제 설계에는 이미 SQS + DLQ + 이벤트 로그가 있었는데,
그때는 그걸 "안정성"으로만 생각했습니다. 사용자 입장에서 보면
**"안 나간 5건, 이유는 키워드 불일치"를 보여줄 수 있다는 것 자체가 기능**이었습니다.

지인들이 말한 것과 해외 사용자가 말한 것이 같은 곳을 가리켰습니다.

> 자동 DM은 만드는 물건이 아니라 **데이터를 모으는 장치**입니다. 만드는 물건은 분석입니다.

### 4단계: 하려던 기능이 API로 되는지 실사했습니다

"팔로우 + 댓글 → DM을 걸어서 팔로워가 얼마나 늘었는지, **누가** 늘었는지, 연령층은 어떤지"를
보여주려 했습니다. Instagram Insights API를 확인했습니다.

| 원한 것 | 결과 |
|---|---|
| 연령·성별·도시 분포 | ✅ `follower_demographics` — 단 **100팔로워 이상** 계정만 |
| 팔로워 수 추이 | ✅ `follower_count` — 동일 제약 |
| **누가 팔로우했는지** | ❌ **팔로워 목록 엔드포인트가 존재하지 않습니다.** 집계만 제공 |
| **게시글별 팔로워 증가 귀속** | ❌ 계정 단위 일별 수치뿐 |

기획의 절반이 API 한계로 불가능했습니다. 우회로도 없었습니다.

여기서 그냥 접지 않고 **되는 방향으로 다시 짰습니다.**
`is_user_follow_business`는 **개인별로** 조회됩니다. 캠페인에 반응한 사람마다 찍으면:

> "이 게시글 반응자 41명 중 팔로워 28명 / 비팔로워 13명"

팔로워 **증가**를 귀속시킬 수는 없지만, **캠페인이 비팔로워를 얼마나 끌어왔는지는 실측됩니다.**
계정 단위 집계가 아니라 게시글 단위 실측이고, 확인해본 상용 도구 중에는 이걸 보여주는 곳이 없었습니다.

## A — Action

### 1. 방향을 세 번 바꿨습니다

**(1) "자동 DM을 만든다" → "분석을 만든다"**

분석을 Phase 4(맨 뒤)에서 Phase 3(주인공)으로 올렸습니다. 이건 순서만 바꾼 게 아니라
**스키마가 바뀌는 결정**이었습니다. 특히 `COMMENT_SKIPPED` + `skipReason` 행을 남기기로 했습니다.

```prisma
model Event {
  type        // COMMENT_RECEIVED | COMMENT_SKIPPED | PRIVATE_REPLY_SENT
              // | USER_REPLIED | FOLLOW_UP_SENT | FAILED
  skipReason? // SELF_COMMENT | NO_KEYWORD_MATCH | DUPLICATE | CAMPAIGN_DISABLED | ECHO
  mediaId     // 비정규화 — 캠페인을 지워도 과거 통계가 남습니다
  latencyMs?
}
```

"왜 DM이 안 갔지?"는 지인들이 가장 많이 할 질문인데, 이 행이 없으면 매번 CloudWatch를 뒤져야 합니다.
**나중에 붙일 수 없는 종류의 결정**이었습니다. 이벤트를 기록하지 않은 과거는 복원되지 않습니다.

**(2) 단일 계정 → 멀티 계정**

"일단 내 계정으로 만들고 나중에 확장"으로 시작했다가 바꿨습니다.
계정 격리는 **모든 테이블의 키 설계**에 들어가는 문제라 나중에 하면 데이터 모델을 통째로 갈아엎어야 합니다.
지금 하면 컬럼 하나입니다.

반면 온보딩 UI, 결제, OAuth 연동은 **나중에 붙여도 데이터 모델이 바뀌지 않습니다.** 그래서 안 만들었습니다.
"지금 해야 하는 확장"과 "나중에 해도 되는 확장"을 가르는 기준이 이것이었습니다.

**(3) DynamoDB → PostgreSQL**

원래 설계는 DynamoDB 단일 테이블이었습니다. 대시보드와 메트릭이 목표에 들어오면서 뒤집혔습니다.
부수 효과로 **멱등성 처리가 오히려 단순해졌습니다.**

```sql
-- 중복 차단과 캠페인 조회를 한 문장으로
UPDATE conversations SET state = 'USER_REPLIED'
 WHERE ig_account_id = $1 AND igsid = $2
   AND state = 'WAITING_USER_MESSAGE'
RETURNING last_media_id;   -- 0 rows = 중복 → skip
```

DynamoDB 설계에서는 별도 멱등성 아이템과 lease를 두고 "PROCESSING 상태로 죽은 워커"를
계속 신경 써야 했는데, 그 고민이 통째로 사라졌습니다.

### 2. 만들려다 만 것 4개

만든 것보다 이쪽이 판단을 설명하기 좋았습니다.

| 안 만든 것 | 이유 |
|---|---|
| **고객별 IAM 유저** | 사용량 과금을 하려고 생각했는데, **고객은 AWS를 호출하지 않습니다.** 모든 호출은 제 Lambda가 하므로 귀속될 요청이 0건이고, 애초에 **AWS 청구에는 IAM 주체별 비용 축이 존재하지 않습니다.** DB 카운터 하나로 대체했습니다 |
| **VPC** | 전부 서버리스라 필요 없습니다. 넣으면 아웃바운드용 NAT Gateway가 월 ~$32 붙고 콜드스타트만 늘어납니다 |
| **AWS QuickSight** | author 1인당 월 $18도 문제지만, **범용 BI 도구는 제가 없애려는 "어려움" 그 자체**입니다 |
| **SAM CLI** | SAM transform은 CloudFormation이 **서버 측에서** 처리합니다. `--capabilities CAPABILITY_AUTO_EXPAND` 하나면 되므로 설치 자체가 불필요했습니다 |

**"고객별 IAM 유저"는 제가 좋다고 생각했다가 뒤집은 케이스입니다.**
과금 단위를 만들려면 AWS 리소스를 나눠야 한다고 무의식적으로 가정했는데,
확인해보니 청구 시스템에 그런 축이 없었습니다. 원가를 계산해보니 **고객 1명당 월 $1 미만**이라
원가 기반 청구 자체가 성립하지 않았습니다.

### 3. 문서를 9개로 쪼갰습니다

2,077줄 한 덩어리라 Phase 3 작업 중에도 Meta webhook 함정 목록까지 통째로 읽게 됩니다.
쪼개는 기준을 **파일 개수가 아니라 "다시 열게 되는지"** 로 잡았습니다.

```
docs/
├── README.md          색인 + 진행 현황        (항상)
├── why.md             배경 · 시장 조사 · 원칙 (한 번 읽고 마는 문서)
├── architecture.md    데이터 모델 · 코드 구조 (코드 쓸 때)
├── meta-api.md        검증된 제약 14개        (★가장 자주)
├── phase-1 ~ phase-4  단계별 할 일 · 검증 · 진행 기록
└── archive/           원본 설계 (오류 지적 헤더를 붙여 보관)
```

원본 설계서는 지우지 않고 **오류 5개를 지적하는 헤더를 붙여 보관**했습니다.
틀린 설계서를 검증으로 잡아낸 이력 자체가 기록할 가치가 있다고 봤습니다.

Phase 문서마다 **`진행 기록`** 칸을 뒀습니다. 이 회고를 쓰면서 확인한 건데,
**막힌 지점을 그때 적지 않으면 나중에 복원되지 않습니다.**

### 4. 저장소 가드레일과 인프라

저장소를 private으로 바꾸고, **시크릿 커밋 차단 훅**을 첫 커밋에 넣었습니다.

```bash
$ ./scripts/precommit-check.sh
커밋 차단: 자격증명으로 보이는 값이 스테이지에 있습니다.
  [AWS 액세스 키]
    1:+AWS_KEY=AKIA...
```

주의한 점은 **문서가 스스로를 차단하지 않게** 하는 것이었습니다.
`meta-api.md`에는 `AKIA`, `IGAA` 같은 패턴 이름이 설명으로 등장합니다.
프리픽스 뒤 길이까지 검사하도록 해서 실제 자격증명만 걸리게 했고, 양방향으로 확인했습니다.

```
차단 테스트 (진짜 형태)   → exit 1  ✅
오탐 테스트 (문서 언급)   → exit 0  ✅
```

`pragma: allowlist` 탈출구도 뒀습니다. 이게 없으면 나중에 테스트 픽스처에 가짜 토큰을 넣을 때
막혀서 `--no-verify`로 훅 전체를 꺼버리게 되는데, 그게 더 위험합니다.

배포용 IAM 유저는 리소스를 `ig-comment-bot-*`으로 제한하고 `PassRole`도 해당 prefix의 role로 묶었습니다.
액세스 키는 화면에 출력하지 않고 임시 파일을 거쳐 프로파일에 주입한 뒤 `shred` 했습니다.

## 곁가지 — 참고하려던 오픈소스가 악성코드였습니다

GitHub에서 별 180개짜리 인스타그램 봇 저장소를 참고하려다 발견했습니다.

- README가 `.su` 도메인의 **원격 PowerShell 스크립트 실행**을 유도하고,
  **실행 정책 우회법까지 친절히 안내**합니다

## 배운 것

### 1. 설계서가 그럴듯하게 읽히는 것과 맞는 것은 별개입니다

제 설계서는 표와 다이어그램과 API 예제까지 갖춰서 완성도가 높아 보였습니다.
그런데 외부 API에 관한 서술 5개가 틀렸고, **전부 컴파일 타임에도 테스트에서도 안 잡히는 종류**였습니다.
webhook이 안 오고, 무한루프가 돌고, 403이 반복되는 식으로 런타임에 조용히 드러납니다.

외부 API를 다루는 문서는 **한 줄씩 공식 문서와 대조**해야 한다는 걸 배웠습니다.
이건 시간이 아깝게 느껴지는 작업인데, 실제로는 며칠짜리 디버깅을 몇 시간으로 줄이는 작업이었습니다.

### 2. "기능이 부족하다"와 "쓰기 어렵다"는 다른 문제입니다

지인들이 말한 건 후자였는데 제가 만들려던 건 전자였습니다.
사용자가 불편을 말하면 기능 요구로 번역하는 습관이 있었던 것 같습니다.

결정적인 확인은 매니챗 리뷰에서 나왔습니다. 평점은 4.6으로 높은데
불만이 과금 모델, 무료 플랜 축소, **분석 부재**에 몰려 있었습니다.
**기능 경쟁에서 이길 수 없는 상대도 다른 축에서는 비어 있을 수 있습니다.**

### 3. 소급해서 만들 수 없는 것을 먼저 정해야 합니다

오늘 내린 결정을 "나중에 해도 되는 것"과 "지금 해야 하는 것"으로 갈라보니 기준이 분명했습니다.

- **지금**: 이벤트 스키마(기록 안 한 과거는 복원 불가), 계정 격리 키(모든 테이블에 영향)
- **나중**: 온보딩 UI, 결제, OAuth, 차트 (데이터 모델이 안 바뀜)

기준은 "나중에 붙일 때 **기존 데이터를 버려야 하는가**"였습니다.

### 4. 좋아 보이는 아이디어를 원가로 검증해야 합니다

"고객마다 IAM 유저를 두고 사용량만큼 청구한다"는 제 아이디어였고 그럴듯했습니다.
그런데 두 가지가 틀렸습니다 — 고객은 AWS를 호출하지 않으므로 귀속될 요청이 없고,
**AWS 청구에 IAM 주체별 비용 축이 애초에 없습니다.**

그리고 원가를 실제로 계산해보니 고객 1명당 월 $1 미만이라 **과금 설계 자체가 불필요**했습니다.
아이디어의 전제를 숫자로 확인하는 습관이 필요합니다.

### 5. 별점은 신뢰의 근거가 아닙니다

별 180개짜리 저장소가 소프트웨어를 담고 있지 않았습니다.
README는 잘 쓰여 있었고 topic 노출도 상위였습니다.
**계정 생성 시각과 저장소 크기라는 두 개의 숫자**가 README 전체보다 많은 것을 말해줬습니다.
