# 로컬에서 전부 통과한 것들이 실제 환경에서 다섯 번 무너졌다

> 2026-09-03 ~ 09-04 · Phase 1 Wave 4 (배포 → Meta 연결 → E2E)
>
> `pnpm verify` 169건이 통과했고 esbuild 번들도 성공했습니다. 배포했더니 모든 요청이 502였습니다.
> 그 뒤로 같은 모양의 무너짐이 네 번 더 있었습니다.

## 배경

Phase 1은 코드·인프라·`/code-review medium` 반영까지 끝나 있었습니다. 그런데 **아무것도
배포되어 있지 않았습니다.** 확인해보니 CloudFormation 스택도, Secrets Manager 시크릿도
존재하지 않았습니다. 남은 일은 배포 → Meta 연결 → 실계정 E2E였습니다.

시작 시점의 상태는 이랬습니다.

| | |
|---|---|
| 테스트 | 169건 통과 (`node --test`) |
| 타입체크 | 통과 |
| Lambda 번들 | esbuild 성공 (4.7MB) |
| 배포 | **없음** |

이 문서는 그 배포와 연결 과정의 기록입니다. 실사용이 드러낸 설계 오류는
[2편](./2026-09-04-2.md)에 따로 적었습니다.

## P — Problem

`scripts/deploy.sh`가 성공했습니다. CloudFormation은 `CREATE_COMPLETE`였습니다.
그리고 모든 요청이 502였습니다.

```
GET /health          -> 502
GET /webhook/nope    -> 502
```

**이 프로젝트에서 두 번째로 겪는 같은 종류의 사고입니다.** 첫 번째는 직전 세션에서
코드 리뷰가 잡았습니다 — `nest build` 산출물에 `node_modules`가 없는데 그걸 통째로
zip해서 배포하면 콜드스타트에서 `Cannot find module 'reflect-metadata'`로 죽는 문제였습니다.
그때 배운 게 "초록 테스트는 배포 가능의 증거가 아니다"였는데, 같은 벽에 또 부딪혔습니다.

문제를 다 풀고 나서 세어보니, **로컬에서 통과한 것이 실제 환경에서 무너진 게 다섯 번**이었습니다.
전부 같은 모양이었습니다.

| # | 로컬에서 통과한 것 | 실제 환경에서 |
|---|---|---|
| 1 | 타입체크 169건 + 번들 성공 | Node 24 런타임이 핸들러를 거부 → 전 요청 502 |
| 2 | Worker 테스트 전부 통과 | 배포 후 **한 번도 실행되지 않음** |
| 3 | `subscribed_apps` → `200 {"success":true}` | 실제로는 필드 절반이 빠진 상태 |
| 4 | Webhooks 테스트 버튼 정상 도착 | 실제 댓글 이벤트만 한 건도 안 옴 |
| 5 | `/privacy` 라우트 작성 완료 | 배포를 안 해서 404 |

## A — Analysis

### 1. 타입체크·테스트·번들이 전부 초록인데 부팅조차 못 함

CloudWatch 로그의 첫 줄이 답이었습니다.

```
INIT_START Runtime Version: nodejs:24.v48
ERROR Init Error {"errorType":"Runtime.CallbackHandlerDeprecated",
  "errorMessage":"AWS Lambda has removed support for callback-based function
  handlers starting with Node.js 24."}
INIT_REPORT Init Duration: 703.22 ms Phase: init Status: error
```

**Node.js 24 Lambda 런타임은 콜백 방식 핸들러 지원을 제거했고, `handler.length === 3`이면
콜백 방식으로 판정해 초기화 자체를 거부합니다.**

```ts
// 죽던 코드 — callback 을 받아서 arity 가 3
export const handler: Handler = async (event, context, callback) => {
  const server = await appCache.run();
  return server(event, context, callback);
};
```

넘기던 `callback`은 `@codegenie/serverless-express`가 쓰지도 않았습니다. 실제 구현은
`async function handler (event, context)`입니다. 파라미터 하나를 지우는 것으로 끝났습니다.

다만 이 라이브러리는 **타입 선언이 자기 구현과 어긋나** 3번째 인자를 요구합니다.
그래서 호출부에는 무시되는 no-op을 넘겨 타입만 맞췄습니다. 중요한 건 우리가 export하는
함수의 arity이기 때문입니다.

```ts
export const handler: Handler = async (event, context) => {
  const server = await appCache.run();
  return server(event, context, () => {});
};
```

**왜 로컬에서 안 잡혔나**: arity 검사는 Lambda 런타임이 합니다. 타입체크·테스트·번들 어디에도
그 검사가 없습니다. 번들 산출물에서 `handler.length`를 찍어보면 3이 나왔겠지만, 그걸
확인해야 한다는 것 자체가 이번에 알게 된 사실입니다.

### 2. Worker는 배포 후 한 번도 실행되지 않았다

API가 살아난 뒤 인프라를 전수 점검했습니다. Lambda×2, SQS+DLQ, 로그 그룹 보존기간까지
템플릿과 정확히 일치했습니다. 그런데 **Worker는 호출 이력이 0건**이었습니다.

API와 Worker는 부팅 경로가 다릅니다.

```
API     → NestJS 부트 → (요청 시) Secrets Manager → Prisma
Worker  → Secrets Manager → 마스터 키 → Prisma → Neon
```

여기서 실패하면 **실제 댓글이 올 때 5번 재시도 후 DLQ로 가서야 알게 됩니다.**
그래서 없는 `igUserId`를 담은 합성 SQS 이벤트를 만들어 직접 invoke했습니다.
`buildContext`가 null을 돌려주는 경로라 DB 쓰기도 Instagram 호출도 없이 부팅 체인만 탑니다.

```json
{"batchItemFailures":[]}
```

```
ERROR 알 수 없는 계정의 이벤트를 건너뜁니다 { igUserId: '000000000000000', ... }
REPORT Duration: 2367.55 ms  Init Duration: 455.64 ms  Max Memory Used: 212 MB
```

기대한 경로가 정확히 돌았습니다. 이 한 번으로 Secrets Manager 권한, 마스터 키 32바이트 디코드,
Lambda→Neon 연결(VPC 밖 공용 인터넷), 배치 응답 형태가 한꺼번에 검증됐습니다.

> **부수 발견**: 이 로그에 node-postgres 경고가 있었습니다. 지금은 `sslmode=require`가
> `verify-full`의 별칭이라 인증서를 완전 검증하지만, **pg v9부터 libpq 의미로 바뀌어
> 검증이 조용히 꺼집니다.** 고객 토큰이 든 DB라 의존성 범프 한 번에 연결이 열리는 건
> 곤란해서 `verify-full`을 명시했습니다. 오늘 동작은 완전히 동일하고, 미래의 강등만 막습니다.

### 3. 외부 API의 성공 응답이 사실이 아니었다

Meta 계정 연결 후 게시물에 댓글을 달았는데 **웹훅이 한 건도 오지 않았습니다.**
`meta-api.md` §6 결정 트리의 1순위 의심 항목이 `subscribed_apps` 누락인데, 우리 스크립트는
그걸 호출하고 `subscribedAt`까지 기록해뒀습니다.

실제 구독 상태를 조회해봤습니다.

```jsonc
// 우리가 받은 응답
{"success": true}

// GET /me/subscribed_apps 의 진실
{"data":[{"subscribed_fields":["messages"]}]}   // ← comments 가 없음
```

**`comments`가 빠져 있었습니다.** 게시물엔 댓글이 3개 달려 있었는데(`comments_count=3`)
받을 구독이 없으니 이벤트가 생길 수 없었습니다.

원인은 순서였습니다. 대시보드 웹훅 구성 **전에** 스크립트를 돌렸고,
**Meta는 앱 레벨에서 구독되지 않은 필드를 조용히 버리면서도 `{"success":true}`를 돌려줍니다.**

이건 제가 쓴 코드의 결함입니다. `meta-api.md` §1-6에 "가장 흔한 삽질"이라고 적어놓고,
정작 스크립트는 `✓ subscribed_apps 호출 성공`이라고 출력했습니다. 응답을 믿었기 때문입니다.

### 4. 테스트 페이로드는 오는데 실제 이벤트만 안 온다

구독을 고친 뒤에도 웹훅이 오지 않았습니다. 여기서 오래 걸렸습니다. 확인한 것들:

| 확인 | 결과 |
|---|---|
| 계정 레벨 구독 | `["comments","messages"]` ✅ |
| 앱 레벨 필드 구독 | 전부 구독됨 ✅ |
| 콜백 URL / 서명 | Webhooks 테스트 버튼이 `COMMENT_SKIPPED / ACCOUNT_MISMATCH` 행을 남김 ✅ |
| 게시물·댓글 | 실재, `comments_count` 증가 ✅ |
| **실제 웹훅** | **0건** ❌ |

테스트 버튼이 남긴 행 하나가 많은 걸 증명했습니다 — Function URL 도달, slug 조회,
App Secret 복호화, **HMAC 서명 검증 통과**, normalize, Event 기록. 서명이 이 프로젝트의
가장 큰 미지수였는데 저장된 Instagram app secret 하나로 통과했습니다
(`parentAppSecret`은 필요 없었습니다).

그런데 이 과정에서 **두 가지를 틀렸습니다.**

**첫째 — 토큰을 엉뚱한 계정으로 발급받았습니다.** `GET /me`가 부계정 `xowls0002026`을
돌려주는 걸 한참 뒤에 알았습니다. 연동 대상은 `hi_im_taetae`였습니다.

원인은 **Instagram 테스터 역할과 앱 관리자 역할이 다른 체계**라는 걸 몰랐던 것입니다.

| 역할 | 대상 | 필요한 것 |
|---|---|---|
| 관리자 | **Meta 계정** | Facebook/Meta 개발자 계정 |
| Instagram 테스터 | **Instagram 계정** | 인스타 아이디뿐 |

대시보드의 토큰 발급 목록에는 **Instagram 테스터 역할이 있는 계정만** 뜹니다. 그때 테스터는
부계정 하나뿐이었고, 그래서 그것만 보였고, 그걸 눌렀습니다. **연동할 본인 계정도
테스터여야 한다**는 게 답이었습니다.

**둘째 — "앱을 게시하지 마세요"라고 조언했다가 정정했습니다.**
라이브 전환과 App Review를 묶어서 봤기 때문입니다. 둘은 별개입니다.

| | 필요한 것 | 우리에게 |
|---|---|---|
| 라이브 모드 전환 | 없음 (토글) | **필요했음** |
| App Review | 심사 제출 | 불필요 (모델 B) |

**개발 모드에서는 수동 테스트 페이로드만 배달되고 실제 활동 이벤트는 발생하지 않습니다.**
역할·구독·서명이 전부 맞아도 그렇습니다. "테스트는 오는데 실제만 안 온다"가 개발 모드의
지문이었는데, 저는 그걸 App Review의 벽으로 잘못 읽었습니다.

### 5. 라우트를 만들고 배포를 안 했다

라이브 전환의 실제 관문은 **개인정보처리방침 URL**이었습니다. 외부 호스팅을 새로 붙이는 대신
이미 공개 HTTPS로 떠 있는 API Lambda에 `GET /privacy` 라우트를 달았습니다.

그리고 그 URL을 대시보드에 넣었더니 거부당했습니다.

```
/privacy -> 404
```

**파일은 만들었고 배포는 안 했습니다.** Meta는 URL을 실제로 가져가서 검증합니다.
배포 후 200이 되자 통과했습니다.

가장 사소한 실수인데, 다섯 개 중 성격이 가장 같습니다 — 내 머릿속에서는 "만들었다"이고
실제 환경에서는 "없다"였습니다.

## A — Action

개별 버그를 고치는 데서 멈추지 않으려고 세 가지를 넣었습니다.

### 1. 초록 배포가 부팅을 뜻하지 않으므로, 배포 스크립트가 직접 확인한다

같은 종류의 사고가 두 번이었습니다(`node_modules` 누락 → 이번엔 핸들러 시그니처).
둘 다 타입체크·테스트·번들이 전부 초록인데 런타임에서만 죽습니다. 그래서 arity만 잡는 게
아니라 **초기화 실패라는 종류 전체**를 잡도록 `deploy.sh` 끝에 붙였습니다.

```bash
STATUS=$(curl -s -o /dev/null -w '%{http_code}' "${FUNCTION_URL%/}/health")
if [[ "$STATUS" != "200" ]]; then
  echo "error: GET ${FUNCTION_URL%/}/health returned $STATUS (expected 200)." >&2
  echo "       ${AWS[*]} logs tail /aws/lambda/ig-comment-bot-${ENVIRONMENT}-Api --since 5m" >&2
  exit 1
fi
```

실패하면 로그 tail 명령까지 찍고 `exit 1`합니다. 이후 모든 배포에서 이 줄이 마지막에
`GET .../health -> 200`을 찍습니다.

### 2. 성공 응답을 믿지 않고 되읽는다

`subscribeApp()` 뒤에 `GET /me/subscribed_apps`로 실제 상태를 확인하고, 필요한 필드가
없으면 **`exit 1`로 죽입니다.**

```ts
await client.subscribeApp();
const subscribed = await client.getSubscribedFields();
const missing = REQUIRED_FIELDS.filter((f) => !subscribed.includes(f));
if (missing.length > 0) {
  console.error(`✗ 구독되지 않은 필드: ${missing.join(', ')}`);
  console.error('  앱 레벨에서 구독하지 않은 필드는 계정 레벨 구독이 조용히 무시됩니다.');
  process.exit(1);
}
```

테스트도 붙였습니다. 그중 하나는 **"일부만 걸린 상태를 그대로 드러내는지"**를 봅니다 —
이 메서드가 존재하는 이유가 그것이기 때문입니다.

### 3. 증상이 안 보이면 추측으로 고치지 않고 관측을 먼저 넣는다

발송 직후마다 `ACCOUNT_MISMATCH` 이벤트가 1건씩 쌓이는데 원인을 모릅니다. 페이로드를
로그에 남기지 않기 때문입니다(개인정보 규칙).

이 계정은 `GET /me`가 `user_id`와 `id` 두 개를 돌려주므로 둘 중 하나로 짐작할 수 있었지만
**고치지 않았습니다.** 대신 실제로 온 `entry.id`를 남기는 `console.warn` 한 줄만 넣었습니다.
다음 실사용 한 번으로 특정되면 그때 고칩니다.

`normalize.ts`는 불변식 #4("순수 함수, I/O 금지")에 따라 로그를 넣을 수 없어서,
이미 `skipped[].igUserId`를 돌려받고 있는 소비자 쪽(`webhook.service.ts`)에 넣었습니다.

### 가장 중요한 결과: 모델 B가 성립한다

**앱에 아무 역할이 없는 제3 계정에서도 자동 DM이 나갔습니다.**

이 프로젝트는 App Review를 가지 않는다는 전제 위에 서 있습니다 — 고객마다 자기 Meta 앱을
만들고, 각 앱이 자기 계정만 다루므로 Standard Access로 충분하다는 구조(`meta-api.md` §4
모델 B)입니다. 디버깅 중에 이 전제가 흔들렸습니다. 댓글 다는 사람은 "자기 계정"이 아니라
제3자인데, 그 사람에게 DM을 보내는 게 Standard Access로 되는가?

제3 계정 테스트가 그 답이었습니다. **라이브 모드 + Standard Access면 일반 사용자에게도
동작합니다.** Phase 2를 막고 있던 가장 큰 불확실성이 해소됐습니다.

## 배운 것

### 1. 로컬 초록불은 "내 환경에서 맞다"는 뜻일 뿐이다

타입체크·테스트·번들은 **내가 만든 모델 안에서의 정합성**을 검사합니다. 실제 환경에는
그 모델에 없는 검사가 있습니다 — Lambda 런타임의 arity 판정, Meta의 앱 모드,
URL을 실제로 가져가서 하는 검증.

두 번 당하고 나서야 개별 버그가 아니라 **경계를 넘는 지점마다 실제로 한 번 찔러보는 것**이
필요하다는 걸 알았습니다. `deploy.sh`의 `curl /health`, Worker 합성 invoke,
`subscribed_apps` 되읽기가 전부 같은 대응입니다.

### 2. 외부 API의 성공 응답은 사실의 증거가 아니다

`{"success":true}`를 받고 실제로는 절반만 적용된 상태였습니다. 이게 위험한 이유는
실패가 조용하기 때문입니다 — 에러도 로그도 없고, 몇 시간 뒤에 "왜 웹훅이 안 오지"로
나타납니다.

**쓰기 요청의 응답보다 그 뒤의 읽기가 진실입니다.** 특히 그 API가 "가장 흔한 실패 지점"이라고
이미 문서에 적어둔 것이라면 더욱 그렇습니다.

### 3. 증상이 안 보이면 관측을 먼저 넣는다

`ACCOUNT_MISMATCH`는 그럴듯한 가설이 있었습니다(`user_id` vs `id`). 고쳤으면 아마 맞았을
겁니다. 하지만 틀렸다면 증상만 덮고 원인은 남습니다. 로그 한 줄이 다음 한 번으로 확정해주는데
추측할 이유가 없었습니다.

### 4. 내 도구가 틀렸을 가능성을 앱 버그보다 먼저 의심한다

위조 서명 POST가 403이 아니라 400을 돌려줬습니다. 앱 버그로 보였습니다.
로그를 보니 에러가 없고 80ms에 끝나 있었습니다 — 핸들러에 닿기 전이었습니다.

원인은 제 curl이었습니다. 작은따옴표 안에서 `\"`가 그대로 남아 `{\"object\":\"instagram\"}`라는
깨진 JSON을 보냈고 Express body 파서가 400을 냈습니다. 다시 보내니 403이었습니다.

**"기대와 다른 결과"와 "버그"는 다릅니다.** 로그가 비어 있다는 사실이 그 구분을 해줬습니다.

### 5. 틀린 조언을 빨리 정정하는 것도 기록할 가치가 있다

"앱을 게시하지 마세요"는 라이브 전환과 App Review를 묶어 본 오판이었습니다.
그 조언대로 갔으면 원인을 훨씬 늦게 찾았을 겁니다. 사용자가 "앱을 게시 안 해서 그런가"라고
물어본 게 재검토의 계기였습니다.

문서에 이미 적혀 있던 문장(§1-11 "Live로 바꿔도 App Review 없이는 안 됨")을 **문맥을
확인하지 않고 적용한 것**이 원인이었습니다. 그 문장은 *비테스터에게 DM 보내는 것*에 대한
서술이지, 웹훅이 발생하는 것 자체와는 다른 층위였습니다.

## 면접용 30초 요약

> 서버리스 파이프라인을 처음 배포했는데 테스트 169건이 전부 통과한 상태에서 모든 요청이
> 502였습니다. Node.js 24 Lambda 런타임이 콜백 방식 핸들러를 제거했고, 핸들러 파라미터가
> 3개면 초기화 자체를 거부한다는 걸 CloudWatch 로그에서 찾았습니다.
>
> 문제는 같은 종류의 사고가 두 번째였다는 겁니다. 직전에도 번들에 의존성이 빠져 콜드스타트에서
> 죽은 적이 있었고, 둘 다 타입체크·테스트·번들이 전부 초록인데 런타임에서만 죽었습니다.
> 그래서 개별 버그를 고치는 대신 **배포 스크립트 끝에 실제 엔드포인트를 호출해 200을
> 확인하고 아니면 실패시키는 검사**를 넣어 초기화 실패라는 종류 전체를 배포 시점에 잡도록
> 했습니다.
>
> 이어서 Meta 웹훅이 한 건도 오지 않는 문제를 디버깅했는데, 구독 API가 `success: true`를
> 돌려주면서 실제로는 필드 절반만 적용한 상태였습니다. **쓰기 응답을 믿지 말고 되읽어서
> 확인하도록** 고치고, 필요한 필드가 없으면 온보딩 스크립트가 죽게 했습니다.
>
> 결과적으로 댓글 → 자동 DM → 답장 → 후속 DM 전 구간이 실계정에서 동작했고, 앱에 권한이
> 없는 제3자 계정에서도 동작하는 것을 확인해 **App Review 없이 서비스가 성립한다는
> 아키텍처 전제를 검증**했습니다.
